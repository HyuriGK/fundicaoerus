# Plano de Segurança — Fundição Erus API

## Vulnerabilidades Críticas Encontradas

### 1. AUTENTICAÇÃO INEXISTENTE (CRÍTICO)
- `src/auth.js` NÃO emite tokens JWT — retorna apenas `{ success, role, name }`
- Frontend marca `localStorage.erus_auth = 'true'` como "autenticado"
- **Qualquer pessoa pode abrir console e digitar `localStorage.setItem('erus_auth','true')` para bypassar o login**

### 2. AUTORIZAÇÃO BASEADA 100% NO CLIENTE (CRÍTICO)
- `src/admin-users.js:14` — middleware `checkDevRole` lê `req.headers['x-role']`
- Frontend envia `x-role: localStorage.getItem('erus_role')`
- **Qualquer pessoa pode enviar header `x-role: desenvolvedor` e ter acesso admin total**
- Mesmo padrão em `src/admin-permissions.js:31`
- Todas as rotas protegidas confiam em header spoofable

### 3. REGISTRO ABERTO SEM CONTROLE (ALTO)
- `/api/register` permite criar contas sem validação
- Sem CAPTCHA, sem rate limiting, sem limite de tentativas

### 4. ZERO RATE LIMITING (ALTO)
- Nenhum middleware de rate limiting em nenhuma rota
- Brute force no login, abuso de API, spam de registro — tudo possível

### 5. SEM HEADERS DE SEGURANÇA (MÉDIO)
- Sem `helmet` — ausente Content-Security-Policy, X-Frame-Options, etc.
- Clicável via iframe (clickjacking)

### 6. ERROS EXPLOSIVOS (MÉDIO)
- Error handler em `api/index.js:240` loga `req.body` completo (pode conter senhas)
- Stack traces expostos em não-produção
- `/api/debug/env` expõe variáveis de ambiente

## Plano de Implementação

### Fase 1 — JWT Authentication (arquivos: `src/auth.js`, `api/index.js`, `lib/middleware.js`)

1. Criar `lib/middleware.js` com:
   - `authenticateToken` — extrai e valida JWT do header `Authorization: Bearer <token>`
   - `requireRole(...roles)` — verifica `req.user.role` contra roles permitidas

2. Atualizar `src/auth.js`:
   - Gerar JWT com payload `{ user, name, role, can_view_monetary }` e expiração de 8h
   - Retornar token no login: `{ success: true, token: '...', role, name, can_view_monetary }`
   - Usar variável de ambiente `JWT_SECRET` (nunca hardcode)

3. Atualizar `src/register.js`:
   - Exigir aprovação (approved = false por padrão já existe, ok)

4. Atualizar `api/index.js`:
   - Aplicar `authenticateToken` como middleware global para todas as rotas `/api/*` exceto:
     - `POST /api/auth` (login)
     - `POST /api/register` (registro)
     - `GET /api` (status)
     - `GET /api/health` (health check)
   - Remover rota `/api/debug/env` em produção (já condicional, mas reforçar)

### Fase 2 — Proteção de Rotas Admin (arquivos: `src/admin-users.js`, `src/admin-permissions.js`, `src/carteira.js` e demais)

1. Atualizar `src/admin-users.js`:
   - Substituir `checkDevRole` (header-based) por `requireRole('desenvolvedor')` usando JWT
   - Usar `req.user.user` ao invés de `req.headers['x-user']`

2. Atualizar `src/admin-permissions.js`:
   - Substituir verificação `x-role` por middleware JWT

3. Atualizar todas as rotas que usam `x-role` ou `x-user`:
   - `src/carteira.js`, `src/faturamento-postgres.js`, `src/refugos.js`
   - `src/pedidos-observacoes.js`, `src/chamados.js`, `src/planner.js`
   - `src/communications.js`, `src/audit-logger.js`, `src/page-locks.js`
   - `src/metas.js`, `src/producao-apontada.js`, etc.
   - Padrão: trocar `req.headers['x-role']` → `req.user.role`
   - Padrão: trocar `req.headers['x-user']` → `req.user.user`

### Fase 3 — Rate Limiting (arquivo: `api/index.js`)

1. Instalar `express-rate-limit`
2. Aplicar rate limits:
   - Login: 5 tentativas / 15 min por IP
   - Register: 3 tentativas / hora por IP
   - API geral: 100 req / min por IP
   - AI assistant: 10 req / min por IP

### Fase 4 — Security Headers (arquivo: `api/index.js`)

1. Instalar `helmet`
2. Aplicar `helmet()` com configuração:
   - Content-Security-Policy adequada
   - X-Frame-Options: DENY
   - X-Content-Type-Options: nosniff
   - HSTS

### Fase 5 — Frontend (arquivos: `public/js/*.js`, `public/*.html`)

1. Criar `public/js/auth-guard.js`:
   - Interceptar todas as chamadas `fetch()` para adicionar header `Authorization: Bearer <token>`
   - Ler token de `localStorage.erus_token`
   - Redirecionar para `login.html` se 401

2. Atualizar `login.html`:
   - Salvar token retornado: `localStorage.setItem('erus_token', data.token)`
   - Limpar token no logout

3. Atualizar `public/session-guard.js`:
   - Incluir token nas requisições de polling

### Fase 6 — Segurança de Erros e Logging (arquivo: `api/index.js`)

1. Remover log de `req.body` no error handler (pode conter senhas)
2. Em produção: mensagem genérica, sem stack trace (já parcialmente feito)
3. Remover ou proteger `/api/debug/env` (apenas em dev com auth)

## Verificação

1. **Testar login**: Fazer login → verificar que token JWT é retornado e salvo
2. **Testar bypass**: Abrir console → tentar `localStorage.setItem('erus_role','desenvolvedor')` → tentar acessar `/api/admin/users` → deve retornar 403
3. **Testar token spoofing**: Enviar request sem token → deve retornar 401
4. **Testar rate limiting**: Fazer 6 logins errados seguidos → deve ser bloqueado
5. **Testar headers**: Verificar response headers com `curl -I` → deve ter CSP, X-Frame-Options, etc.
6. **Testar frontend**: Login normal → navegar pelo sistema → deve funcionar sem erro
